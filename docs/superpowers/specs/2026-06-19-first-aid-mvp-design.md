# Design Spec — Entrenador WFA · MVP (Foundation + Module 1 "Aprender")

> Date: 2026-06-19
> Status: Approved for implementation planning
> Source requirements: `docs/PRD - Entrenador WFA.md`, `docs/Motor de Escenarios - Diseño.md`
> Content contract: `docs/contenido-cav.yaml`, `docs/casos.yaml`

## 1. Scope

This spec covers **Phase 0 (Foundation) + Phase 1 (Module 1 "Aprender")** from the PRD's suggested build phases (§11). Modules 2 (Practicar) and 3 (Escenarios) are explicitly **out of scope** for this iteration but the architecture is built so they plug in without rework.

**In scope:**
- Scaffolding: Vite + React + TypeScript, PWA shell, content build pipeline.
- Shared design system ("Field Manual" visual direction).
- Content loader: YAML → JSON (build-time), validated with zod, typed.
- Storage wrapper (IndexedDB + in-memory fallback) — built and tested, but Module 1 does not yet persist user state.
- Module 1 "Aprender": chain map (advance organizer), node detail, worked example, quick reference.

**Out of scope (future iterations):**
- Module 2 (SRS, generative recall formats, elaborative feedback engine).
- Module 3 (scenario engine, action bank, scoring, debrief).
- LLM, backend, accounts, multiplayer, free-text grading.
- i18n (Spanish hardcoded), dark mode, search.

**Success criterion for this iteration:** A user can open the app offline on mobile, navigate the full Cadena de Atención (Escena → HABCDE → Secundaria → Evacuación), expand any node to read its `significado / detalle / por qué`, walk through one worked example, and consult the quick-reference. The `rationale` text shown is read from the single source of truth so Modules 2/3 can later reuse it.

## 2. Decisions (locked during brainstorming)

| Topic | Decision | Rationale |
|---|---|---|
| Stack | React + Vite + TypeScript + `vite-plugin-pwa` | Mature ecosystem, first-class TS, simple static deploy, mobile perf OK. |
| Content pipeline | Build-time YAML → JSON via Vite plugin; zod-validated; generated types | Zero runtime parser, smaller bundle, autogenerated types, build fails on bad content. |
| Storage | IndexedDB via `idb-keyval` wrapper, in-memory fallback | Large quotas, async, robust; ready for Module 2 SRS state. |
| Language | TypeScript | Type safety over content models catches inconsistencies at build. |
| Code/UI language | **Code in English, user-facing text and `.yaml` content in Spanish** | User instruction. Identifiers/files/comments/commits in English. |
| Visual direction | **Field Manual** — cream/burgundy, serif headings, "worn AIDER notebook" | Chosen from 3 mockups. |
| Hosting | Vercel / Netlify (static, auto-deploy per PR + production on main) | Custom domain, good DX, SPA fallback. |
| Module 1 home | Chain map with clickable nodes (advance organizer R1.1) | Anchors every detail to the chain visually. |
| Architecture | **Feature-first** (`modules/<name>/{content,domain,ui,routes}`) with `shared/` for cross-cutting | Each module understandable in isolation; delete = delete a folder. |
| Routing | `react-router-dom` v6 with `HashRouter` | No server-side config needed; PWA-safe. |

### 3.2 Layer dependency rules (enforced by ESLint `import/no-restricted-paths`)

- `shared/*` **never** imports from `modules/*`.
- `modules/<X>/*` may import from `shared/*`, never from `modules/<Y>/*`.
- Within a module: `routes` → `ui` → `domain` → `content` (no cycles).
- `shared/content/` imports only zod + JSON. `shared/domain/` and any module `domain/` import no React but **may** import `shared/domain` (e.g. the rationale map). A module's `content/` holds raw-data selectors only; view-model projections that need rationale lookups live in the module's `domain/` (this is why `chainModel.ts` sits under `learn/domain/`).

### 3.3 State

- v1 uses local React state only (accordion open-state, expanded section). No global store.
- Zustand deferred until cross-route shared state appears (Module 2 SRS).
- No Module 1 user state is persisted in v1 (the PRD's R1.x requirements do not require persistence). The storage wrapper exists and is tested for Module 2.
- **Optional, decided as included:** "last visited node" is persisted (key `progress:learn:lastNode`) so the chain map can show a subtle "continuar" affordance. This is the one storage consumer in v1 — small, demonstrates the wrapper end-to-end. If it complicates implementation it may be dropped without affecting other requirements.

## 4. Content pipeline

### 4.1 Flow

```
docs/contenido-cav.yaml ┐                                  ┌─ src/shared/content/generated/content.json
docs/casos.yaml         ┴─▶ scripts/build-content.ts ──────▶┤
                              parse → map → zod validate    └─ src/shared/content/generated/cases.json

src/shared/content/loader.ts ◀── imports generated JSON statically (Vite bundles + tree-shakes)
```

A small Vite plugin runs `build-content` on `buildStart` and re-runs on `.yaml` change (HMR). The build **fails loud** (non-zero exit, prints `path: issue`) if any YAML violates its schema — guaranteeing clinical-content fidelity before merge.

### 4.2 The YAML is heterogeneous — schemas model it faithfully

The content files are **not** a flat list of uniform nodes. Concretely:

- `siglas[]` — each is an acronym. Some expose `letras[]` (HABCDE, AVDN, MUESTRA, DIAS, PILAR, SOAP), others expose `componentes[]` (TEV, MSC), others are definition-only (MDD). Optional `nota`, `definicion`. `es_secuencia` marks order-significant acronyms.
- `cadena[]` — 4 phases (`escena`, `primaria`, `secundaria`, `evacuacion`), each with a **phase-specific** `contenido` object:
  - `escena.contenido`: `seguridad`, `bioseguridad`, `mecanismo_dano`, `numero_victimas`, `impresion_general` (ref to `tev`), `buscar_ayuda`.
  - `primaria.contenido`: `previo`, `presentacion`, `detalle_por_letra` (ref to `siglas.habcde`), `reglas` (refs to `reglas_practicas`).
  - `secundaria.contenido`: `intro`, `linea_base`, `orden`, `reevaluacion`, `signos_vitales` (ref), `anamnesis` (ref `muestra`), `examen_fisico` (ref `dias` + extra).
  - `evacuacion.contenido`: `contactar_ae`, `evaluacion_continua`, `comunicacion`, `posicion` (ref `posicion_victima`), `niveles` (ref `niveles_evacuacion`).
- Plus top-level: `signos_vitales`, `posicion_victima`, `reglas_practicas[]`, `niveles_evacuacion[]`, `temas_clinicos[]`, `tarjetas[]` (Module 2, validated but unused in v1).
- `worked_example` — **new block authored for R1.6** (does not exist in the YAML yet; see §5.5). Shape: `{ titulo: string, steps: [{ fase: enum(escena/primaria/secundaria/evacuacion), estado: string, accion: string, racional_ref: string }] }`. Each `racional_ref` must resolve to an existing concept id (same ref-integrity pass as `cadena`/`siglas`). Authored and clinically reviewed in build-order step 6.

**Schema strategy:** zod models each of these shapes precisely (phase content as a discriminated union on `fase`). Refs (`ref_sigla`, `ref`, `concepto`, `racional_ref`) are validated as strings at parse time; **referential integrity** (every ref resolves to an existing id) is checked by a dedicated validation pass in `build-content.ts` that fails the build on a dangling ref.

### 4.3 Field mapping (Spanish YAML keys → English schema)

`scripts/build-content.ts` maps the Spanish snake_case YAML keys to English camelCase via an **explicit, documented** mapping table (no automatic transform — clinical content must be deliberate). Examples:

| YAML (es) | Schema (en) |
|---|---|
| `siglas` | `acronyms` |
| `sigla` / `nombre` | `acronym` / `name` |
| `letra` / `significado` / `detalle` | `letter` / `meaning` / `detail` |
| `componentes` | `components` |
| `racional` / `racional_ref` | `rationale` / `rationaleRef` |
| `es_secuencia` | `isSequence` |
| `cadena` / `fase` / `contenido` | `chain` / `phase` / `content` |
| `niveles_evacuacion` / `nivel` / `criterio` | `evacLevels` / `level` / `criterion` |
| `reglas_practicas` / `regla` / `concepto` | `practicalRules` / `rule` / `concept` |
| `temas_clinicos` | `clinicalTopics` |
| `signos_vitales` | `vitalSigns` |
| `tarjetas` | `cards` |
| `worked_example` / `steps` / `estado` / `accion` | `workedExample` / `steps` / `state` / `action` |

Phase enum values map: `escena→scene`, `primaria→primary`, `secundaria→secondary`, `evacuacion→evacuation`. **User-visible strings (titles, rationale text, criteria) are NOT translated** — they stay Spanish; only the keys are anglicized.

### 4.4 Loader & rationale map

```ts
// loader.ts — static import + validate-once + memoize
export function loadContent(): Content   // validates content.json against schema on first call
export function loadCases(): Cases       // validates cases.json
```

Double validation (build + runtime) is intentional: runtime parse (~ms) catches transit corruption and fails early via the ErrorBoundary. May be downgraded to a type-cast in production if it ever costs measurable perf.

```ts
// shared/domain/rationale.ts — the M2/M3 reuse contract
export function buildRationaleMap(content: Content): Map<string, string>
export function getRationale(conceptId: string, map: Map<string, string>): string | undefined
```

The rationale map indexes every `rationale` by its concept id (from `acronyms`, `chain` phases, `clinicalTopics`, `practicalRules`). Module 1 shows it as the "por qué"; Modules 2/3 will look it up by `rationaleRef`/`concepto`. **No rationale text is duplicated in the UI** (PRD §9).

**Concept-id uniqueness (build guard).** Because these ids come from multiple sources and a collision would silently overwrite a map entry (wrong "por qué", no error), `build-content.ts` runs a uniqueness pass: it collects every id-producing source and fails the build with `Duplicate concept id: {id}` if any id appears in more than one source. A fixture with a deliberate duplicate id asserts the build fails. This makes the 1:1 rationale contract that Modules 2/3 depend on actually guaranteed.

## 5. Module 1 "Aprender"

### 5.1 Chain model projection

`modules/learn/content/chainModel.ts` projects the heterogeneous `cadena` + `siglas` + refs into a uniform **navigable node tree** for the UI:

```ts
interface ChainPhase { id: PhaseId; title: string; rationale: string; nodes: ChainNode[] }
interface ChainNode {
  id: string                 // route param, e.g. "habcde-h", "scene-safety", "evac-decision"
  phase: PhaseId
  title: string              // Spanish, user-facing
  subtitle?: string
  icon?: IconId              // for non-letter nodes
  letter?: string            // for HABCDE / acronym letters
  kind: 'acronymLetter' | 'acronym' | 'topic' | 'reference'
  items: NodeItem[]          // expandable sub-items (meaning/detail/why)
  rationaleId?: string       // resolves via rationale map
}
// Note: no per-node severity in v1. CRÍTICO/GRAVE/LEVE (the Chip severities)
// are a property of niveles_evacuacion only (PRD), not of procedural HABCDE
// steps — conflating them would mislead. The evac decision node renders the
// three Chips for the evacuation levels; individual chain steps do not carry severity.
interface NodeItem { label: string; detail: string; why?: string }
```

The projection is a **pure function** `buildChainModel(content): ChainPhase[]`, fully unit-tested with the fixture. This is where the data heterogeneity is normalized once, so the UI components stay simple.

### 5.2 Routes

| Path | Component | Requirements | Data |
|---|---|---|---|
| `/` | `ChainMap` | R1.1 | `buildChainModel(content)` grouped by phase |
| `/chain/:nodeId` | `NodeDetail` | R1.2, R1.3, R1.4, R1.5 | node from model + resolved rationale |
| `/example` | `WorkedExample` | R1.6 | `content.workedExample` (see §5.5) |
| `/quickref` | `QuickRef` | R1.7 | acronyms + vitalSigns + evacLevels (flat) |
| `*` | redirect → `/` | — | — |

### 5.3 Screens

**`ChainMap` (`/`)** — Advance organizer. Vertical phase timeline: each phase a numbered burgundy marker + uppercase label + serif title + a list of `NodeCard`s. The **Primaria** phase renders H/A/B/C/D/E `LetterBadge`s to anchor the strict order visually; other phases use a per-node lucide icon. Bottom quick-links → `/example` and `/quickref`. Stateless (derives from model). Shows optional "continuar donde dejaste" if `progress:learn:lastNode` exists.

**`NodeDetail` (`/chain/:nodeId`)** — Hero: breadcrumb · large `LetterBadge` (56×56) or icon · serif title · italic subtitle. Body renders the node's `items[]`:
- For acronym nodes (letras/componentes): an accordion of `ExpandableItem`s, one per letter/component, each showing `label (significado)` + `detail` + `why (rationale)`.
- For topic/reference nodes: `Section` blocks (`Significado` / `Detalle` / `Por qué`), one idea per screen (R1.5 segmentation; long `detail` rendered as bullet list).
In-page footer: `← Anterior` / `Siguiente →` from `findPrevNext`. Writes `progress:learn:lastNode` on mount.

**`WorkedExample` (`/example`)** — Narrated clean pass through the chain (R1.6). Scroll narrative of alternating cards: scene state → action taken → why (rationale, linked to its `/chain/:nodeId`). One idea per card (chunking).

**`QuickRef` (`/quickref`)** — Dense "see everything" mode (R1.7). Collapsible sections: **Siglas** (each as a letter/meaning/detail table), **Signos vitales normales** (table from `vitalSigns`), **Niveles de evacuación** (Chip + criterion). Sans typography (Inter), no animation, fast scan.

### 5.5 Worked example source (decision, not TBD)

`casos.yaml` cases have a Module-3 shape (`acciones_clave`/`distractores`/`revelaciones`) unsuited to a *narrated* worked example, and `casos.yaml` is the Module-3 content contract. Therefore the worked example is authored as a **new `worked_example` block inside `docs/contenido-cav.yaml`** (the Module-1 source of truth): an ordered list of `{ phase, state, action, rationaleRef }` steps narrating one clean pass (based on the "Caída en descenso" example, simplified). This keeps Module-1 content self-contained and editable as data (no hardcoding), and is schema-validated like the rest.

## 7. PWA, offline & storage

### 7.1 PWA

- `vite-plugin-pwa`, `generateSW` (Workbox) strategy, `registerType: 'autoUpdate'`.
- Precache all hashed `dist/` output: `globPatterns: ['**/*.{js,css,html,json,woff2,png,svg,webmanifest}']`, `maximumFileSizeToCacheInBytes: 5 MiB`. No external runtime caching (everything is local static).
- Manifest: `name: "Entrenador WFA"`, `short_name: "WFA"`, `display: standalone`, `orientation: portrait`, `background_color: #f4ede0`, `theme_color: #7a1f1c`, `lang: es-AR`, icons 192/512/maskable.
- Offline UX: `useOnlineStatus()` hook; `Shell` shows green "Offline-ready" when SW active, never an error (offline is the feature). Update toast: "Nueva versión disponible. Recargá." No custom install prompt in v1 (browser-native).

### 7.2 Storage (`shared/domain/storage`)

```ts
interface KV {
  get<T>(k: string): Promise<T | undefined>
  set<T>(k: string, v: T): Promise<void>
  del(k: string): Promise<void>
  clear(): Promise<void>
}
// getStorage() probes IndexedDB once; on failure returns an in-memory Map-backed KV.
```

- Keys namespaced `<domain>:<entity>:<id>` (constants in `keys.ts`), e.g. `progress:learn:lastNode`, `meta:storageVersion`.
- Versioned migrations (`migrations.ts`) run on boot; v1 = version 1, no migrations (skeleton ready for M2).
- Robustness: Safari Private Mode / quota-exceeded caught → silent memory fallback, `console.warn`, UI never breaks (PRD §5).
- v1 consumer: only `progress:learn:lastNode` (§3.3).

## 8. Error handling

- **Build:** zod failure or dangling ref → non-zero exit, printed `path: issue`. CI blocks merge.
- **Runtime content parse:** failure caught by `shared/app/ErrorBoundary.tsx` → "Contenido no disponible" screen (should never trigger if build passed).
- **Storage:** all ops wrapped; failure → memory fallback, no UI impact.
- **Routing:** unknown path → redirect to `/`.

### 9.3 CI (`.github/workflows/ci.yml`)

`npm ci` → `content:check` → `lint` → `typecheck` → `test:run` → `build`. `content:check` first so bad clinical content fails fast.

### 9.4 Performance budget (informal)

JS gzip < 100 KB (single module). Lighthouse mobile on preview deploy: Performance ≥ 90, A11y ≥ 95, PWA installable. No third-party analytics/tracking.
